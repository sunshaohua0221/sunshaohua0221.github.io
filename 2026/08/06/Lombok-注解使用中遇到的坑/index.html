Lombok 注解使用中遇到的坑

Lombok 通过注解在编译期帮我们生成 getter/setter/构造器，省去了大量样板代码，用熟了确实回不去。但如果只知其然而不知其所以然，很容易在运行时才暴露问题——而且往往还是「本地好好的，一到测试/生产就炸」。本文把最近在几个项目里陆续踩到的四个典型坑整理出来：@Builder 默认值失效、与 MapStruct 注解处理器冲突、继承场景属性丢失、缺少无参构造函数导致序列化失败。每个坑都按「现象 → 原因 → 解法」展开。

1. @Builder 导致默认值失效

现象

定义一个带默认值的配置类：

期望 OrderConfig.builder().build() 能得到 status="PENDING"、retryCount=3、autoConfirm=true。但实际拿到的是 status=null、retryCount=0、autoConfirm=false——所有默认值全部丢失。

原因

@Builder 在编译期为类生成一个「全参构造器」和一个内部 Builder 类。Builder 的字段默认是 null/基本类型零值，而 build() 调用的是那个全参构造器：

字段初始化器 = "PENDING" 确实写在类里，但它和构造器体里的赋值 this.status = status 同时存在——构造器一旦执行，就把字段覆盖成了 Builder 传进来的 null。初始化器在构造器赋值之前执行、之后被覆盖，所以默认值永远不生效。

关键认知：@Builder 用的是「全参构造器」，而不是「字段初始化器」。builder 不传的字段，会以构造参数默认值（null/0/false）进入构造器，直接覆盖掉你在字段上写的默认值。

解法

用 @Builder.Default 标记需要保留默认值的字段：

@Builder.Default 会把这个字段的初始化逻辑从「字段初始化器」挪到 Builder 里：builder 不显式赋值时，就使用注解里写的默认值。此时 OrderConfig.builder().build() 就能正确得到 status="PENDING"、retryCount=3、autoConfirm=true。

经验：只要字段有默认值、又用了 @Builder，一律加上 @Builder.Default，养成肌肉记忆能少踩很多坑。

2. 与 MapStruct 等注解处理器冲突

现象

项目同时引入 Lombok 和 MapStruct，编译时随机出现类似报错：

或者 MapStruct 生成出来的 Mapper 实现类没有正确调用 setter，反序列化后字段全是 null。

原因

Lombok 和 MapStruct 都是注解处理器（Annotation Processor），它们在编译期的同一轮（round）里运行。MapStruct 生成 Mapper 实现时需要读取目标类的 getter/setter/构造器，但这些信息是 Lombok 在编译期才生成的。

如果两个处理器的执行顺序不对——MapStruct 先于 Lombok 运行——MapStruct 看到的就只有「源码」，而不包含 Lombok 生成的访问方法，于是报「找不到符号」或生成了错误的映射代码。

这类问题最烦人的地方在于「不稳定」：IDE 里能编过（IDE 自己做了增量处理），Maven/Gradle 全量构建就挂；或者换台机器、换个 JDK 版本就时好时坏。

解法

核心是让 MapStruct 在生成代码时「看得到」Lombok 的产物。推荐两步：

第一步，引入 lombok-mapstruct-binding（MapStruct 官方提供的桥接注解处理器，专门把 Lombok 的生成模型暴露给 MapStruct）：

第二步，确保注解处理器的顺序为 Lombok → lombok-mapstruct-binding → MapStruct。上面 annotationProcessorPaths 的声明顺序即执行顺序，写成 Lombok 在前即可。

经验：只要项目里 Lombok + MapStruct 一起用，就固定把 lombok-mapstruct-binding 加进 annotationProcessorPaths，能省掉一大类「找不到符号」的诡异编译错误。如果目标类用 @Builder，还可以在 Mapper 上用 @Mapper(uses = ...) 引导 MapStruct 走构造器注入。

3. 继承场景下的属性丢失

现象

父类持有通用分页字段，子类扩展查询条件：

用 UserQueryReq.builder().keyword("tom").build() 构建后，page/size 丢了——要么是 0，要么直接编译不过。

原因

普通的 @Builder 只作用于当前类的字段，不会把父类的字段纳入 Builder。父类虽然也加了 @Builder，但子类 Builder 并不知道父类的构造参数，于是父类的属性无法被赋值，最终落到默认值或 null。

关键认知：@Builder 是「非继承友好」的。它在编译期生成的是当前类的 all-args 构造器和对应 Builder，整条继承链上的字段并不会自动串起来。

解法

改用 @SuperBuilder（Lombok 1.18.4+ 引入，专为继承场景设计）。注意：继承链上的每一个类都必须加 @SuperBuilder，缺一不可。

4. 缺少无参构造函数导致序列化失败

现象

一个用 @Builder（或 @Value）标注的 DTO，在被 Jackson 序列化/反序列化时，启动或运行时抛出：

原因

Jackson、JPA/Hibernate、Hessian、Spring 等框架在做反序列化或反射实例化时，默认需要一个无参构造函数。

  • @Builder 只生成「全参构造器」，不会生成无参构造器；
  • @Value（不可变类）更是只生成全参构造器，字段全是 final，连 setter 都没有；
  • 即便已经加了 @Data，如果同时又加 @Builder，虽然 @Data 隐含的 @RequiredArgsConstructor 在没有 final 字段时会给无参构造器，但 Jackson 反序列化还需要 setter，单靠无参构造器 + @Value 的 final 字段照样失败。

更隐蔽的坑：很多人下意识补一个 @AllArgsConstructor，结果和 @Builder 生成的「全参构造器」签名完全一样，直接编译报错「Constructor with same erasure is already defined」。

解法

现代最干净的方案是用 Lombok 1.18.14+ 提供的 @Jacksonized——它会在 @Builder 基础上自动为 Jackson 加上 @JsonCreator 和 @JsonProperty，让 Jackson 直接走 Builder 反序列化，无需无参构造器：

针对 JPA 实体的额外提醒：Hibernate 要求实体有非 private 的无参构造器，用 @Builder 的实体要补 @NoArgsConstructor（必要时再加 @AllArgsConstructor 配合 @NonNull 字段）。

5. 最佳实践总结

  1. 默认值 + @Builder = 必加 @Builder.Default。否则 Builder 不传的字段一定被覆盖成 null/零值。
  2. **Lombok + MapStruct 务必引入 lombok-mapstruct-binding**，并在 annotationProcessorPaths 中保持 Lombok 先于 MapStruct 的顺序，避免「找不到符号」类编译错误。
  3. 继承链上的 Builder 一律用 @SuperBuilder，且父子类都要加，普通 @Builder 无法串联父类字段。
  4. 序列化/DTO/Entity 慎用裸 @Builder / @Value。需要被 Jackson/JPA 反序列化时，优先用 @Jacksonized，或补齐 @NoArgsConstructor + @Data；不要随手补 @AllArgsConstructor 与 @Builder 撞车。
  5. 多看编译产物别只看 IDE。Lombok 的很多坑在 IDE 增量编译下不暴露，全量构建或换环境才炸——CI 里固定跑一次干净构建最稳妥。
